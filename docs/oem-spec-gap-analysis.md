# 零跑 OEM 规范对照：我们的实现差在哪

> 对照对象：`QLP_YSJ_0225-2026 诊断设计规范`、`QLP_YSJ_0224-2026 软件下载规范`
> 对照基准：`ota-core` 当前实现
> 目的：分清「实现偏差」与「范围外」，为面试表述和后续改进提供依据

---

## 0. 先明确层级关系

```
ISO 14229-1 / ISO 15765-2     国际标准，最低要求
        ↓
零跑 QLP_YSJ 企业规范          在 ISO 之上加严，冲突时以企业规范为准
        ↓
具体 ECU 的诊断需求书           项目级裁剪与补充
```

规范原文：

> 本文件不会取代现有的国际标准文件，但它对标准的内容增加了额外的要求和限制。
> **如有冲突，本文件优先于规范性文件。**

所以：**按 ISO 实现不算错，但按零跑规范会查出若干不符合项。**

## 1. 完整刷写流程对照

零跑的流程分成四个 Part，我们只实现了 Part3 的核心三件套。

| Part | 内容 | 我们的状态 |
|---|---|---|
| **Part1 预编程** | `22 F197`/`F150`/`F189` → `10 03`（功能寻址）→ `85 01` 关 DTC → `28 03` 关通信 | ❌ 无 |
| **Part2 进编程模式** | `10 02` → `27 11`/`27 12` → `31 6000` 查文件合法性 → `31 6001` 查版本 → `2E F198` 工具序列号 → `2E F199` 编程日期 | 🔶 只有 `10 02` + `27` |
| **Part3 下载** | SBL 下载 → `31 0202` 检查 → `31 FF00` 擦除 → `34`/`36`/`37` → `31 0203` 校验 → `31 FF01` 依赖性检查 → `11 01` 复位 | 🔶 只有 `34`/`36`/`37` |
| **Part4 后编程** | `10 03` → `28 00` → `85 01` → `14 FFFFFF` 清 DTC → `10 01` | ❌ 无 |

## 2. 差异清单

标注说明：

- **实现偏差** — 我们做了，但做法与规范不符，属于真实的实现问题
- **范围外** — 规范要求，但我们这个项目的目标范围内没有这一项
- **已一致** — 碰巧或有意做对了

### 2.1 严重：`maxNumberOfBlockLength` 低于规范下限

| 项 | 内容 |
|---|---|
| 规范 | `maxNumberOfBlockLength` 绝对最小值 `0x0402`，最大值 `0x0FFF` |
| 我们 | 返回 `74 20 02 00`，即 `0x0200` = **512** |
| 类型 | **实现偏差** |
| 证据 | [uds.c](../ota-core/src/core/uds.c#L312-L315) |

```
512 = 0x0200 < 0x0402（1026）
→ 低于规范允许的最小值
```

**后果**：44824 字节的包要发 89 块（实机日志正好 89 个 `0x36`）。
若用 `0x0402`（1026），块数降到约 44；若用 `0x0FFF`（4095），降到约 11。

**为什么当初选 512**：省 RAM（块缓冲只占 512 B，MCU 只有 192 KiB）。
**代价**：不符合规范，且刷写时间变长。

### 2.2 严重：安全访问锁定后的 NRC 与持久化都不对

| 项 | 规范 | 我们 | 类型 |
|---|---|---|---|
| 锁定期 NRC | `0x37`（RequiredTimeDelayNotExpired） | `0x36`（ExceededNumberOfAttempts） | **实现偏差** |
| 等待时间 | 10 秒 | 只有 `lockout_started_ms`，需确认是否真的等 10 s | **实现偏差** |
| 错误计数器存储 | **非易失性存储器** | 仅 RAM 字段 `key_failures` | **实现偏差** |
| 上电检查 | 每次通电/复位检查计数器 | 无 | **实现偏差** |

规范原文：

> 在第三次错误访问尝试后，ECU 应等待 10 秒，然后才再接受另一条安全访问的"请求种子"消息。
> 错误访问计数器应存储在 ECU 的非易失性存储器中。每次通电/复位时，ECU 应检查计数器。

**最严重的是第三条**：计数器只在 RAM，拔电即清零，锁定形同虚设。

**修正方向**：把 `key_failures` 与 `lockout_started_ms` 移入元数据（EEPROM），上电时读出并继续计时。

### 2.3 严重：连续请求种子应返回同一个种子

| 项 | 规范 | 我们 |
|---|---|---|
| 连续 `27 01` | 返回**相同**种子，错误计数器从第二次起 +1 | 每次都生成**新**种子（`request_count++`） |
| 类型 | **实现偏差** |

```
规范为什么要求同一个：
  tester 可能没收到种子应答而重发 27 01
  若 ECU 换了种子，tester 用旧种子算的 key 必然失败
  → 白白消耗一次尝试机会，三次后就被锁
```

**修正方向**：`request_count` 只在"一次 key 发送序列开始"时递增；同一序列内重复 `27 01` 返回缓存的种子。

### 2.4 中等：擦除应是独立例程，不是 `34` 顺带做

| 项 | 规范 | 我们 | 类型 |
|---|---|---|---|
| 擦除入口 | `31 01 FF00` 独立例程 | `0x34` 内部直接 `external.erase()` | **实现偏差** |
| 擦除次数计数 | 每次擦除尝试使刷写次数计数器 +1 | 无 | **实现偏差** |
| 擦除前状态 | 将 APP 软件置为不可用 | 只有删除标记的 `0x37` 才落盘 | **实现偏差** |

规范原文：

> 该功能在每次尝试擦除时，将使尝试刷写次数计数器增加 1。APP 软件将被设置为不可用。

**为什么要分开**：`34` 顺带擦会让 tester 无法控制擦除范围，也无法在擦除前把"APP 可用"标志置无效。

### 2.5 中等：校验与版本检查应是例程，不在 `37` 里

| 例程 | RID | 职责 | 我们的位置 |
|---|---|---|---|
| 检查文件合法性 | `31 01 6000` | 验证书链 | ❌ 无 |
| 检查版本 | `31 01 6001` | 版本不得低于当前；ECU 内部版本须与 `F189` 一致 | `0x37` 内部 |
| 检查次级引导加载程序 | `31 01 0202` | SBL 完整性 | ❌ 无 SBL |
| 检查已下载数据 | `31 01 0203` | **SHA256** 比对包头摘要 | `0x37` 内部（CRC32） |
| 依赖性检查 | `31 01 FF01` | 软硬件兼容性，成功后把 APP 置有效 | ❌ 无 |

规范还规定：

> 失败后 `2E(F198、F199)`、`34`、`31(FF00)` 均应返回 **NRC 0x22**，
> 同时存储失败状态到 DID **`F1ED`**。

**我们的差距**：`0x37` 失败只回 `0x72`，tester 无法区分是哪一步失败；也没有 `F1ED` 可读。

### 2.6 中等：签名体系是两级证书链，我们是单层签名

| 项 | 零跑 | 我们 |
|---|---|---|
| 算法 | RSA2048 + PKCS1 填充 + SHA256 | Ed25519 |
| 结构 | CA 私钥签 X.509 证书 → 临时密钥对签文件头 | 直接用私钥签镜像 payload |
| ECU 侧 | 必须把 **CA 公钥存非易失存储**，丢失即无法刷写 | 公钥编译进 Bootloader |
| 类型 | **范围外**（工程取舍，非错误） |

**为什么真实项目用证书链**：CA 密钥可以在不动 ECU 的前提下轮换（换的是证书），单层签名做不到。

**我们的定位**：Ed25519 更现代、代码更小，适合学习项目；但不能说"实现了零跑的验签体系"。

### 2.7 中等：没有 SBL（次级引导加载程序）

| 项 | 规范 | 我们 |
|---|---|---|
| SBL 存放 | **易失性存储器**（RAM） | 无 |
| 职责 | 具备擦写主 Bootloader 之外区域的能力 | 主 Bootloader 直接擦写 |
| 主 Bootloader 保护 | 区域受硬件写/擦除保护 | 未启用 WRP |

**为什么用 SBL**：主 Bootloader 逻辑越简单越可靠，且永远不用更新。把"擦写能力"放进临时的 SBL，主 Bootloader 就能保持最小。

### 2.8 轻微：几项协议细节

| 项 | 规范 | 我们 | 类型 |
|---|---|---|---|
| DLC | 应始终为 8，ECU 应忽略 DLC≠8 的帧 | 未体现 | **实现偏差** |
| 功能寻址 | 物理寻址 + 功能寻址并行；`3E 80` 功能寻址不需回应 | 只有物理寻址 `0x7E0` | **范围外** |
| 进编程会话前置条件 | 车速 ≤ 3 km/h、车辆非 Ready | 无 | **范围外** |
| 供电范围 | 9~16 V 才允许重编程 | 无 | **范围外** |
| 低功耗 | 引导程序中 I/O 应进最低功耗模式 | 无 | **范围外** |
| 总线关闭恢复 | 10 ms 内检测并恢复 | 无 | **范围外** |

### 2.9 一条规范要求，正好对应我们的设计

规范原文：

> 如 `36` 服务在数据传输过程中，ECU 接收到的 `36` 数据块内容的连续帧出现丢帧的情况，
> ECU 应能在上位机尝试重发时继续下载。
> 例如 ECU 在接收 `36 05` 时因丢帧未能给出 `76 05`，上位机重发 `36 05`（重发次数不大于 3 次），
> ECU 重新接收到完整的 `36 05` 后应正常继续。

**这正是我们"重复块"机制的设计目标**：块号相同 → 读 NOR 比对内容 → 一致就只回应答不重写。

> ⚠️ 注意区别：规范说的是**ISO-TP 连续帧丢帧**（一条多帧消息没拼完），
> 我们处理的是**整条 `36` 消息重发**。逻辑上能覆盖，但严格说不是同一层。

## 3. 已经一致的部分

| 项 | 规范 | 我们 |
|---|---|---|
| 首帧视为序号 0，第一个 CF 序号为 1 | 明确 | 一致 |
| SN 到 15 后回 0 | 明确 | 一致 |
| 多帧最大 4095 字节 | 明确 | 一致（ISO-TP 实现） |
| `BS = 0`、`STmin = 0` | 表 7 明确 | 一致 |
| `P2Server` = 50 ms | 表 6 | 一致 |
| `P2*Server` = 5000 ms（一般 2000） | 表 6 | 需确认 |
| `34` 单次最大 4 GB | 明确 | 一致（uint32） |
| `36` 单条最多 4095 字节 | 明确 | 我们限制 512，未超上限 |
| 长流程回 `NRC 0x78` | 擦除和传输都可能需要 | 未实现（见待办） |
| `0x34`/`0x36`/`0x37` 仅编程会话 | 表 3/4 | 一致 |
| `0x28`/`0x85` 仅扩展会话 | 表 3 | 不适用（未实现） |

## 4. 这份对照怎么用

### 4.1 面试表述

```
不要说："我按 ISO 14229 实现了 UDS 服务端"
要说："我按 ISO 14229 实现，并对照过零跑的《诊断设计规范》和
     《软件下载规范》做过差距分析。知道量产规范在 ISO 之上
     还加了哪些要求，也知道自己的实现还差哪几条。"
```

### 4.2 主动说差距

```
"我的 maxNumberOfBlockLength 回 512，低于零跑规范的 0x0402 下限，
 当时是为了省 RAM，代价是刷写块数从 11 涨到 89。

 安全访问的错误计数器我只放在 RAM，规范要求存 NVM 且锁定期回 0x37，
 这条是我的实现问题。

 擦除我做在 34 里面，规范要求独立例程 31 01 FF00 并计数，
 这属于范围外，因为我的项目没有 SBL。"
```

**能分清「我做错了」和「我没做这一块」，是最能体现工程判断的表达。**
