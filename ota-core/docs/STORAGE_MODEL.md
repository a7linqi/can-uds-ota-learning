# v0.2 存储与恢复约定

## 分区与地址

所有端口地址都是相对于各自器件的字节偏移。UDS 下载地址是 App 的逻辑绝对地址，由服务端映射到外部下载区，不可把外部 Flash 当作 MCU 内部 Flash 寻址。

| 器件 | 区域 | 偏移 | 长度 |
|---|---|---:|---:|
| 内部 Flash | Bootloader | 0 | 64 KiB |
| 内部 Flash | 唯一 App，含向量表 | 0x10000 | ZG 960 KiB / ZE 448 KiB |
| 外部 NOR | 待安装镜像容器 | 0 | 1 MiB |
| 外部 NOR | 已确认旧版备份容器 | 0x100000 | 1 MiB |
| AT24C02 | 元数据 A | 0 | 64 B |
| AT24C02 | 元数据 B | 128 | 64 B |

外部 NOR 的 2 MiB 是本核心要求分配的区域，不是对开发板实际 Flash 型号/容量的确认。AT24C02 是 2 Kbit，即 256 字节，不是 2 KiB。

固件只为 0x08010000 链接。外部存储器中的两个容器不执行，不涉及双执行槽重链接。内部 App 第一项是 MSP，第二项是 Thumb 复位入口；镜像头只存在外部容器中。末次内部写入按 4 字节补 0xFF，CRC 只覆盖真实 payload。

## 外部镜像格式

固定 32 字节头，所有字段采用显式小端编码，不直接落盘 C 结构体。

| 字节偏移 | 字段 | 约束 |
|---:|---|---|
| 0 | magic | IMG2 |
| 4 | version | 非零，严格高于已确认版本 |
| 8 | image_size | payload 字节数，不含头 |
| 12 | payload_crc | payload CRC32 |
| 16 | load_address | 必须为 0x08010000 |
| 20 | flags | 当前必须为 0 |
| 24 | reserved | 当前必须为 0 |
| 28 | header_crc | 覆盖头部前 28 字节 |

校验还检查 MSP 的 RAM 范围/8 字节对齐、复位入口的 Thumb 位以及入口落在 payload 范围内。范围校验不能证明应用指令有效，更不能代替实际启动测试。

这是与旧 L1 不兼容的 IMG2 格式：旧槽位地址、旧头格式及旧 0x31 健康确认语义不能继续使用。

## 元数据事务

64 字节记录包含 magic、序号、状态、旧版 version/size/CRC、新版 version/size/CRC、尝试次数、已确认版本下限、保留字段、CRC 和 commit。

每次更新仅写另一个物理副本：

1. 清零目标副本最后 4 字节 commit，并读回确认已经失效。
2. 按 EEPROM 8 字节页边界写前 60 字节，包含 CRC。
3. 最后写 4 字节 commit。
4. 读回整个记录，逐字节比对，成功后才更新调用者的内存对象。

全过程保留之前的有效副本。读写驱动失败时不假装成功；只要任一副本不可读取，就返回 I/O 错误，避免选择未知旧记录后覆盖新记录。两份均可读但均无效时，Bootloader 留在恢复入口。

序号采用模 2^32 的半范围比较，支持 UINT32_MAX → 0；正好差半圈或相同序号而内容冲突时拒绝判定。

## 状态与恢复

~~~mermaid
flowchart TD
    I["IDLE：已确认版本"] --> D["DOWNLOADING：仅写外部下载区"]
    D --> R["READY：包已完整提交"]
    R --> N["INSTALLING：备份完整后安装"]
    N --> T["TRIAL：先记录尝试再启动"]
    T -->|App 健康确认| I
    T -->|未确认或新 App 损坏| B["RESTORING：恢复外部备份"]
    B --> I
~~~

| 持久状态 | 本次允许改变什么 | 复位后如何处理 |
|---|---|---|
| DOWNLOADING | 外部下载区 | 启动仍完整的旧 App；下载从头重发 |
| READY | 外部备份区 | 重新备份旧 App，旧 App 尚未擦除 |
| INSTALLING | 内部 App 区 | 重验下载包与备份，从头擦写 App |
| TRIAL | 元数据尝试计数 | 成功记录次数后才允许启动；第 4 次进入恢复 |
| RESTORING | 内部 App 区 | 重验旧备份，从头恢复，校验后提交 IDLE |
| IDLE | 正常运行 | 用元数据中的长度/CRC 校验内部 App |

第一次装机没有历史镜像：试启动失败后留在 Bootloader，清除失败候选，允许重新下载；不能声称恢复了不存在的旧 App。若已有旧版但备份损坏或存储器持续 I/O 失败，保持 Bootloader，不跳转损坏 App；多重介质故障后的维修刷写策略仍需后续设计。

升级确认只提升到实际确认的版本。新候选未确认时，允许按已记录的旧版元数据恢复。版本策略依赖可写 EEPROM，不能宣称具备防物理篡改的安全防回退能力。

## UDS 接口变化

- 0x34 只接受 0x08010000；size 是 32 字节头 + payload 的总长度。
- 0x74 返回 74 20 02 00：最大 TransferData 请求总长 512 字节，因此数据部分最多 510 字节。
- TransferData 的 BSC 由 1 开始，FF 后允许 00。重复上一块时比对已落盘的完整字节；相同则仅重发确认，不重复写；不同或跳号返回 NRC 0x73。
- 0x37 必须收到精确长度并通过 CRC、向量/地址及版本策略检查，才提交 READY。元数据写入失败不会返回下载成功。
- 0x31 / RID 0001 仅验证 READY 包，不能模拟 App 的健康确认。
- 默认 S3 为 5000 ms；集成层必须周期调用 uds_poll()，超时清除易失下载状态和解锁状态。
- 0x11 只提出复位请求；真实端口必须在响应发完后复位。
- F195 目前返回 Bootloader 核心演示版本 0.2.0；App 版本保存在元数据中，尚未增加单独的 App 版本 DID。
- 0x27 是演示算法；本轮未实现升级包签名。

## 端口接入条件

flash_port_t 分别实例化为 internal 和 external，eeprom_port_t 独立实例化。接口必须串行使用；目前没有互斥锁或 FreeRTOS 任务。底层 write 返回成功前必须等待器件实际写完。

内部驱动负责扇区边界、4 字节编程、错误标志及超时；SPI 驱动负责 NOR 页拆分、WREN/WIP、擦除和超时；EEPROM 驱动负责 I2C 地址、ACK polling 和超时。metadata.c 已按 8 字节 EEPROM 页拆分。

真实擦除耗时、掉电时器件的实际行为、外设初始化/关中断、MSP/VTOR 切换、SysTick/DMA 清理、看门狗以及通讯响应等待仍需真机工程验证。这里没有 Keil scatter 文件或可烧录固件。

## 故障验证范围

每次模拟复位都重建 CAN/UDS/Bootloader/端口对象，只保留三个存储器中的字节。模型检查内部 Flash 扇区边界、4 字节写入对齐、NOR 只能 1→0、EEPROM 页边界，并可在写/擦中间停止后续存储访问。

测试镜像约 1 KiB、1.5 KiB，另用约 128 KiB 包验证 BSC 回绕；故障切点取样不等于穷尽所有真实器件失效方式。主机模型不模拟 EEPROM 同页旁扰、实际擦除电压、I2C/SPI 时序、CAN 错误帧或电源波形。L3 才能以继电器分阶段断电验证这些假设。
