# STM32 长操作与 0x78

STM32 诊断调度器为 `0x34/0x36/0x37/0x31` 增加了协作式长操作处理。协议核心仍是同步存储接口；这是 main 上下文中的调度与服务回调，没有创建线程或在 ISR 中擦写。

1. 完整请求进入待处理缓冲区后，先发送对应 SID 的 `7F SID 78`。
2. 返回主循环，等待 ISO-TP、软件发送队列和硬件 CAN 邮箱空闲。初始等待超过 1000 ms 时不开始存储操作。
3. 运行实际 C UDS 处理函数。NOR 端口在每个擦除扇区、写页和读取调用前后提供服务点；EEPROM 读写也提供服务点。
4. 服务点只处理 CAN 发送和等待应答，不重新进入 UDS 请求分派。每隔约 1000 ms 发一次新的 `0x78`，结束后才发送最终结果。

当前会话通告 P2=50 ms、P2*=5000 ms。处于服务端处理阶段时暂停 S3 的空闲计时，最终应答完成后重新开始。RoutineControl 即使请求了正应答抑制，已经发送 `0x78` 后也会返回最终结果，避免客户端一直等待。

## 必须满足的 BSP 条件

单次外部存储调用必须在 1000 ms 内返回，或者在等待 WIP/ACK 的循环内从 main 上下文调用 `ota_firmware_service()`。该函数不能从 ISR 调用，也不能递归进入诊断分派；返回负数时驱动应退出。

超过服务间隔限制或检测到 CAN 发送错误时，停止后续存储操作并关闭当前运行期的编程门控。已经完成的写入不会撤销，重新上电时由原有事务元数据决定恢复路径。不能把客户端超时理解为设备一定没有写入。

回调无法强行中断一段已经阻塞的 HAL/芯片调用。服务间隔超限检查是在获得执行机会后发现问题；不能据此宣称具备硬实时保证。单银行内部 Flash 擦写可能阻塞取指，因此它在复位后的安装阶段执行，没有用这个机制宣称内部擦除期间 CAN 可正常服务。看门狗和从 RAM 执行驱动仍未加入。

## 已验证的行为

`tests_stm32/test_stm32.c` 在两种 Flash 容量、关闭/开启门控两种配置下运行。新增验证包括：

- 虚拟 40 ms/扇区的 1 MiB 擦除，等待应答间隔小于 P2*，最终才返回 `0x74`。
- 初始 `0x78` 的硬件邮箱未空闲时，EEPROM/NOR 都不开始写。
- 初始发送长期不能完成、CAN 发送失败、BSP 调用超过 1000 ms 后停止后续操作。
- 出错后拒绝新的写入请求，诊断读取仍可使用。
- 长操作跨越 `uint32_t` 毫秒计数回绕。
- 带延迟的镜像 CRC 检查、EEPROM 提交和 `0x31` 最终应答。
- 全程不擦写内部 App 区。

这些是可控虚拟时钟和内存设备的检查。真实 SPI Flash、EEPROM、CAN 仲裁与 HAL 时延尚未测量；默认工程门控仍为 0。
